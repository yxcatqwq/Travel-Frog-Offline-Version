# 旅行青蛙单机版：本地服务实现清单

审计日期：2026-09-10。目标是让现有客户端在没有原服务器的情况下，能够读取、修改、推进并保存游戏状态，最终支持“在线账号状态导出为文件 → 单机版导入 → 继续游戏”。本轮只整理需求，不修改游戏逻辑。

当前最需要补的是**本地权威状态、业务结算、事件调度和持久化**。界面能够打开、客户端有某个 Model，均不代表相应玩法已经本地化。

## 1. 审计范围与证据

以现有 `offline_build/travel_frog_local_native.apk` 中的 `assets/game/js/main.min.js` 为主要依据，检查协议表、调用点、回调、39 个注册模型、事件消费逻辑，并核对离线补丁、资源清单和原始 APK 中的相关方法。

| 项目 | 数量/结论 |
|---|---|
| `ProtocolList` 定义 | 245 个，全部列入附录 |
| 静态字符串形式直接发送的协议 | 185 个；未直接发送的定义不能据此判废 |
| 注册的非空协议回调名 | 95 个，其中 17 个不在上述协议表 |
| 协议定义、发送点与回调名的去重并集 | 262 个入口；不是 262 个独立玩法，也不是都要复制在线机制 |
| `ModelList.modelClassList` | 39 个注册模型 |
| `TimerEvent.Type` | 30 个值，含 `NONE`，即 29 个非空类型 |
| 本地服务 | 未发现替代原服务器的完整实现；现有补丁主要使加载与进入场景可继续 |

可复查的配套文件：

- [协议逐项清单及全部定时事件类型](audit/protocols.md)：262 个入口的参数、调用/回调符号、初步处理方式。
- [可用 Excel 打开的协议清单](audit/protocols.csv)。
- [39 个模型索引](audit/models.md)：方法、观察到的成员、回调。
- [机器可读审计结果](audit/inventory.json)：计数、符号位置、源码 SHA-256。
- [源码节选](audit/source-excerpts.txt)：模型、入口、工作台/堆肥箱、协议分发和事件消费逻辑。
- [配置资源目录](audit/config-resources.json)：`config.eab` 中由资源清单声明的配置名。

复查命令：在项目根目录执行 `python tools/audit-local-requirements.py`。脚本只读 APK，重新生成 `docs/audit`。

**“完整”的边界：**这是针对当前客户端版本可见依赖的完整工作清单，不是原服务器源码的完整规格。请求参数名可以静态提取，完整响应结构、真实概率、隐藏进度、服务器任务队列等不能仅凭客户端确定。下文将“代码已证实的依赖”“需要设计的本地机制”“仍待确认的原版规则”分开说明。原生 SDK 内部接口、远程 H5 玩法和未随包发布的内容也不能由 262 个入口涵盖。

## 2. 已有内容与真实缺口

| 当前内容 | 已有能力 | 仍缺什么 |
|---|---|---|
| 本地启动 | 加载打包的脚本、资源，避开原登录流程与启动遮罩 | 从有效存档装载所有模型后再进入场景；加载失败可恢复 |
| `NetworkControl.login` | 直接设置 `syncComplete=true` 并调用回调 | 原本由 `client_load_all_info` 等同步的账号状态、各玩法状态、推送与事件 |
| 新手状态 | `SettingsInfo.guideStep=Complete`，另有部分引导标记补丁 | 原服务器曾发放的资产、有效蛙状态、解锁与设施数据、一次性奖励记录 |
| 钱包 | 显示、设置余额、余额检查 | `addClover/addTicket` 是空方法；`consumeClover/consumeTicket` 只检查，不扣款 |
| 库存 | `doAddHouseItem/doConsumeHouseItem` 有内存变更和刷新能力 | `addHouseItem` 不执行入库，`consumeHouseItem` 只检查；在线流程依赖 `item_update` 等实际更新 |
| 背包/桌子/设施槽位 | 某些操作先改内存或等待成功回调再改内存 | 统一校验、所有权转移、失败回滚、持久化、计时结果 |
| 天气 | 存在天气消费者与资源选择逻辑 | 当前补丁把季节资源键固定为 `31`；真实天气/时段生成与状态更新仍缺 |
| 存储 | cookie/localStorage 工具、界面偏好、采草重试记录等 | 未发现完整账号存档及可导入导出的权威状态。`GameData.sav` 等常量的存在不代表已接通保存链路 |
| 动画、照片合成、界面 | 很多素材、布局和结果展示可复用 | 触发这些画面的有效数据；生成下一次事件的本地规则 |

钱包/库存的上述空方法在原始在线 APK 中也存在，属于原本依赖服务端下发更新的设计，不能归因于离线补丁删掉了实现。迁移时也不能简单把所有空方法填成“直接增减”，否则客户端预操作和本地响应可能重复发奖或扣款。

### 工作台和堆肥箱为什么不显示

- 工作台：`FurnitureModel.isOpen()` 判断 `serverData.shop.start_time > 0`。当前默认值为 0，因此 `MainOutView.updateFurniture()` 显示空工作台位置并隐藏进入按钮。`shop.leave_time` 还单独控制家具商人的在场时间，不能把“工作台解锁”和“商人始终在场”混成一个状态。
- 堆肥箱：`MainOutView.update_compost()` 读取 `compostData.show_index`，从 `compost_list[show_index-1]` 查已拥有的箱子，再由 `CompostData` 配置取贴图。当前 `show_index=0`、列表为空，自然没有可用箱子贴图。
- 工作台还需要有效的 5 个工具位、5 个材料位以及锁定状态；堆肥箱需要 6 个投料位、当前处理槽和阶段。只补贴图会留下空面板、操作失败或无法推进的问题。
- 已观察到 `furniture_load_compost` 派发的是 `UPDATE_TUMBER`，而部分其他堆肥操作派发 `UPDATE_COMPOST`。需核对控制器订阅、启动刷新和推送刷新路径，避免状态修复后界面仍不更新；本轮不把它直接断言为唯一显示原因。

**初始状态原则：**新建存档可以采用“新手教程已完成”的产品设定，但“教程完成”与工作台、堆肥箱等后续解锁并不等价。若希望新档直接拥有基础设施，应把它们列为明确的初始赠送项。导入账号则忠实保留原解锁状态，不能无条件套用新档模板，也不能每次启动重复赠送。

## 3. P0：所有玩法共用的本地基础设施

P0 是依赖基础；P1 是基础可玩闭环；P2 是扩展玩法完整性；P3 是在线专属或版本兼容处置。优先级不代表可以丢弃导入账号的低优先级数据。

| 编号 | 必须补齐的本地内容 | 完成标准 |
|---|---|---|
| A01 | 本地权威状态容器：唯一存档身份、各子系统状态、修订号；界面模型为投影或受控访问者 | 一个操作只有一个最终结算来源，切换场景不重新初始化资产 |
| A02 | 本地请求适配器：覆盖协议调用、参数校验、返回码、异步回调、无回调命令、异常与取消 | 现有窗口不会因等待网络永远卡住；非法请求不假装成功 |
| A03 | 响应与推送分发：兼容 `ServiceDispatcher`、Model 回调、Controller/UI 事件；保持必要顺序 | 数据先更新再展示结果；回调只执行一次；支持附带状态更新的响应 |
| A04 | 启动同步：本地身份 → 存档读取/迁移 → 配置就绪 → 时间追赶 → 模型装载 → UI 刷新 → 同步完成 | 不能仅设置 `syncComplete`；缺存档新建，坏存档可恢复，不以默认空数据冒充已加载 |
| A05 | 持久化：完整状态序列化、原子提交、备份、自动保存、异常中断恢复 | 购物/领取后立即杀进程重进，状态一致；保存失败不能提示已成功保存 |
| A06 | 事务与幂等：资源扣除、物品移动、奖励、事件确认、任务进度作为一次提交 | 双击、重复回调、重放事件、崩溃重启均不重复结算；不能负库存或出现物品复制 |
| A07 | 本地时钟：统一时间单位、导入时间锚点、时区/日界线、前后台切换、时间回拨策略 | 活动、邮件、商人、称号等使用同一时间基准；设备时间异常不使队列死循环 |
| A08 | 持久化调度器：开始/截止/下次刷新时间、任务类型和负载、唯一任务 ID、离线补算 | 关闭应用期间旅行/生长/制作仍可在重进时正确结算；长期离线按规则处理多个任务 |
| A09 | 随机与规则版本：可重放的随机结果或随机状态、配置版本、结算版本 | 同一已生成奖励重进不重新抽；概率/上限有明确来源或标为本地规则 |
| A10 | 存档校验与迁移：缺字段补齐、数组长度/索引/ID/时间检查、跨版本迁移、未知字段保留 | 修复旧空状态存档时保留已有进度；不覆盖正常的“未解锁”或“没有物品”状态 |
| A11 | 配置服务：复用包内配置，替代远端功能开关/活动配置，记录规则版本 | 静态素材存在不等于活动开放；被引用的物品/照片/家具 ID 可解析 |
| A12 | 本地诊断与验收工具：操作日志、未支持协议清单、受控时间推进、固定随机测试、存档前后差异 | 能定位“数据缺失、未解锁、资源加载失败、刷新失败”各类问题；诊断命令不混入正常玩家流程 |

`core.SocketManage.AnalysisProtocol` 的现有路径会先派发注册的协议事件，再调用匹配 session 的回调，并支持不带 session 的服务器主动命令。本地适配层必须理解这套契约，不能只做一个统一的 `{code:0}` 返回器。

## 4. P1：基础游戏与设施

### B01. 新手、角色与设置

- 本地职责：创建/恢复身份、蛙名、当前状态和动作、头像、称号及到期时间、展示照片、创建时间；本地改名和费用；各引导标记及新手奖励领取状态。
- 存档内容：`client_load_role` 中的 `uid/res/settings/frog/misc` 对应数据；`settings.client` 原为 JSON 字符串，导入时要解析并保留未识别键；`hasOpenedDesk/guideFurniture/guideDrawing/guideCamera` 等不能只用一个总开关代替。
- 入口：`UserModel/RoleModel`，`client_load_role/client_set_name/client_rename_cost/client_set_achieve/client_set_icon/client_set_pic_show/client_set_client`，4 个 `tutorial_*` 协议。
- 验收：新档具有合法的蛙状态与道具数据；导入未完成教程或未解锁设施的账号时按既定策略处理并报告，不隐式全解锁。

### B02. 钱包、库存和统一奖励

- 本地职责：三叶草、兑换券和玩法资源余额；物品持有数量、堆叠/上限、消耗品与非消耗品；礼包及自选礼包；收藏登记；错误码和不足提示。
- 保存：资产数量、唯一/重复物品关系、已领取奖励、自选礼包待选内容、购买记录；重建 `itemDataAll/itemDataList` 等索引，不直接序列化 `core.Dictionary` 实例。
- 入口：`ItemModel/UserModel`，`item_load_items/item_update/item_update_ticket/clover_update/item_gift_open/item_load_select_gift/item_select_gift`。
- 验收：所有买卖、装包、送礼、投料、邮件、抽奖、归家奖励都通过同一结算机制；无重复更新。`sub_clover` 是结果动画显示用的临时扣留量，不应当成第二种货币导入。

### B03. 三叶草田、生长与收割

- 本地职责：生成草位、种类与成熟时间；三叶草/四叶草/特殊产物；收割后再生；离线生长；堆肥或其他设施对草田的影响。
- 保存：各草位 ID、种类/产物、`last_harvest` 等时间、待确认收割与去重信息。画面位置缓存与实际生长数据分开。
- 入口：`RoleModel`，`clover_load_clovers/clover_harvest/clover_harvest_resend/clover_notice_get`。
- 验收：采一次只入账一次；采完重启不恢复成未采状态；离线成熟不要求应用常驻。生长周期/产量需从配置和后续样本确认。

### B04. 商店、购买与兑换券抽奖

- 本地职责：商品可售条件、价格、次数/持有上限、购买扣款和入库；消耗抽奖券、抽中结果、领奖/兑换状态；免费商品策略。
- 保存：`purchasedMap` 对应购买记录、待领取奖品、刷新/重置周期和已用次数。
- 入口：`item_load_shop_info/item_buy/item_gacha/item_redeem_prize`；配置 `shopData/Item/Prize`。
- 验收：同一操作原子扣款入库，余额不足不变；退出抽奖界面重进不丢奖、不重抽。`lottery_*` 是另一套玩法，见 C12。

### B05. 行囊与桌子

- 本地职责：行囊 4 槽、桌子 8 槽，允许物品类型、放入/取出/替换、准备完成和锁定、蛙外出时的限制、冲突提示。
- 保存：`bagDataList/deskDataList/bagLock` 对应权威数据；明确物品究竟在库存、行囊还是桌子，避免多处重复拥有。
- 入口：`item_putin_bag/item_takeout_bag/item_putin_desk/item_takeout_desk/item_set_bag_completed`。
- 验收：反复放取数量守恒；准备完成可驱动出发；出发消耗、回家剩余物品按规则回流。

### B06. 蛙的生活与旅行状态机

- 本地职责：在家休息/吃饭/读书/写字/制作、准备出发、外出、寄照片、归家、再次休息；行囊与桌子影响；道具消耗；目的地/路线/同行者选择；旅行耗时、步数与成果结算。
- 保存：当前状态及动作、状态开始/结束时间、进行中的旅行上下文、携带物品快照、已确定的结果、归家待展示/已结算标记。
- 入口：`RoleModel/TravelModel`，`client_load_role/client_load_events/notify_new_event`，`TimerEvent.GoTravel/BackHome/Return/Picture`。
- 验收：至少完成“准备 → 自动出发 → 离线推进 → 寄照片 → 归家 → 收奖励 → 再出发”的闭环。当前未发现一个可直接调用的独立“出发请求”；不能把接收/播放旅行事件等同本地旅行模拟。
- 待确认：时间、目的地和照片权重、道具效果、返家掉落、隐藏进度。客户端有相关常量和配置引用，是否足够还需解码/核对，不能宣称已恢复原服务器算法。

### B07. 照片、相册与回收

- 本地职责：旅行照片生成及层组合；待保存、已保存、删除与恢复；相册分页、容量、排序；新照片提示和动态相册/礼品盒引用。
- 保存：照片实例 ID、模板 ID、完整 `layers`、生成时间、来源、保存/删除状态和跨模块引用；不能只保存相册数量或图像缩略图。
- 入口：`TravelModel`，全部 9 个 `album_*`；配置 `Picture/PictureTag`；已有照片生成/对齐工具可复用为资源工作流，不等于游戏内成果生成规则已实现。
- 验收：两张相同模板照片仍可具有不同实例和层数据；删除、恢复、导出导入后引用一致；懒加载照片有完整内容。

### B08. 邮件与结果事件队列

- 本地职责：邮件生成、分页、未读/已读/已领、附件与过期、容量；旅行等结果事件的排队、确认和去重；新邮件/新事件/红点推送。
- 保存：邮件 ID、内容、附件、时间和领取状态；事件 `id/evt_type/evt_value/evt_string` 等原始负载、展示进度/确认状态与结算标记。
- 入口：`TravelModel/MessageModel`，`mail_load/mail_load_mails/mail_open/mail_read`，`client_load_events/client_confirm_event/notify_new_event/notify_new_mail/notify_redmsg/notify_reward`。
- 验收：中途关闭奖励动画不会丢奖或重复领奖；导入已经结算但尚未展示的事件，不再次加钱。`Result.eventSystem` 负责消费/展示，仍需本地生产与持久化队列。

### B09. 家具、工作台与家具商人

- 本地职责：工作台解锁；工具/材料 10 槽、锁定、配方、材料占用 `mate_list`、蛙制作动作、制作时长与完成结果；心情/罢工；家具拥有、摆放/待更换；商人到来/离开、货架与库存、购买。
- 保存：`serverData.shop/mood/bench_lock/bench/put_fur/has_fur/mate_list/replace_fur` 以及本地制作任务的截止时间、输入和预定结果。
- 入口：`FurnitureModel`，`furniture_load_furniture/furniture_buy_shop/furniture_putin_bench/furniture_takeout_bench/furniture_replace_fur`；`TimerEvent.FurnitureFinish/FurniturePut/FurnitureVersion`。
- 验收：已解锁工作台可见且能进入，材料数量守恒；制作可离线完成；商人离开不让已解锁工作台消失；摆放与睡眠/制作动作正确引用家具资源。

### B10. 堆肥箱与土地状态

- 本地职责：拥有/摆放/更换堆肥箱；6 槽投料和取料校验、当前处理槽锁定、加工阶段推进、消耗与产出/土地效果；这些效果的具体公式待确认。
- 保存：`compostData.show_index/replace_index/compost_list/state/box_index/box_list`，以及本地加工时间和未领取产物（若规则需要）。
- 入口：`furniture_load_compost/furniture_replace_compost/furniture_putin_box/furniture_takeout_box`。
- 验收：有效拥有数据决定图像；界面、土地阶段和操作状态一致；投料后重启可继续，完成一次只消耗/产出一次。不要用周期性强制显示掩盖空状态。

### B11. 庭院其他设施与装饰

- 本地职责：不倒翁拥有与摆放；口袋/存草设施的展示、积累和收取；花盆展示、种植/成熟/收获；庭院装饰拥有、切换、消耗与状态。
- 保存：`tumblerData`、`pocketData` 的 `list/show_index/replace_index/clover`、`flowerpotData.show_list/list/plant_list`、`RoleModel` 装饰相关字段及相应计时任务。
- 入口：`furniture_load_tumbler/furniture_replace_tumbler/furniture_load_pocket/furniture_replace_pocket/furniture_pocket_get/furniture_load_flowerpot/furniture_flowerpot_harvest/client_load_decorate/client_change_decorate`。
- 验收：已拥有但未摆放与未拥有分开；收获、积累上限、切换和资源引用一致。花盆的加载回调不在协议定义表中，也必须纳入启动恢复。

### B12. 任务、成就与解锁关系

- 本地职责：采集、购物、旅行、来访、制作等行为增加任务进度；单任务奖励、列表/阶段奖励；称号/收藏/玩法解锁；一次性领取。
- 保存：`GuideTaskModel.data/dataList/dataReward` 对应任务进度、奖励状态，`RoleModel` 成就及到期时间，各玩法独立解锁字段。
- 入口：5 个 `task_*`，`client_set_achieve/client_load_role`；配置 `taskData/Achieve/GoalNumber`。
- 验收：不能只根据“打开某页面”的 `task_client_pro` 增加所有进度；本地结算动作应产生业务事件；奖励与解锁在同一事务中落盘。

### B13. 季节、昼夜与天气

- 本地职责：季节、`hours_type`、天气产生/切换、离线恢复、关联动作和设施表现；加载所需资源组。
- 保存：`WeatherModel.data` 与时间锚点；随机天气若已确定，重启保持一致。
- 入口：`weather_load`，`getSeasonKey/getSeasonCover/getSeasonPartical/getSeasonSpine`。
- 验收：解除固定 `31` 后，不同季节/夜间仍有完整背景、房屋、土地、工作台和特效；跨时段不会只换背景而模型状态不变。

## 6. P3：联网、运营与版本兼容内容

这些内容必须有明确处置，不能保持原样等待服务器；也不能一律返回成功。下面是实现方向建议，尚未决定的奖励与活动策略不是已经实现的功能。

| 编号 | 内容 | 单机版需要做什么 |
|---|---|---|
| D01 | 账号认证、token、重连、心跳、远端踢线 | 用本地存档身份替代运行期依赖；`NetworkModel` 是注册壳，流程主要在 `NetworkControl`。保留必要生命周期接口；正常离线不触发无限重登 |
| D02 | 充值/礼包权益、水与兑换系统 | 已拥有权益照常保存；`RechargeModel.data` 中 `water/change/field/sack`、`giftData` 等游戏数据应本地化；支付下单/取消与这些状态分开处理，不能伪造原平台交易。水、田地等实际推进规则仍需核对 |
| D03 | 激励广告与分享奖励 | `AdsModel/ShareModel` 的次数、冷却、已领取状态本地保存；为新获取奖励选择直接领取、替代任务或关闭入口等规则；所有相关按钮明确可用或不可用，不静默无响应 |
| D04 | 排行榜、点赞、其他玩家资料 | `RankingModel` 可改为本地历史榜/记录，或停用；不能把旧快照说成实时在线排行；不影响本地收藏和进度 |
| D05 | 贺卡交换、社交分享、漂流/互动内容 | 可保留历史内容；跨玩家部分需要本地 NPC/模拟、文件交换或只读方案，分别说明；单机端不向原服务器发送命令 |
| D06 | 礼包码、平台活动票据、淘宝导入、微信专属奖励 | 保存已兑换/已获得记录；新兑换要定义本地码表或停用。不能承诺离线验证官方一次性码；旧淘宝导入接口不是我们要实现的通用账号快照导入器 |
| D07 | 公告、功能开关、活动目录、远端资源 | `NoticeModel/ActivityModel` 本地配置替代；公告已读、宣传图领奖/弹出次数保存。核对 `clientconfig/system_normal/publicity_map/recharge_merch/activity/cityroam/video_x36` 等 SDK 公告来源 |
| D08 | 地图/H5/跨应用/视频内容 | `travelmap/cityroam` 等可能依赖远程页面、URL 或其他应用；逐项决定打包实现、离线说明或隐藏。不能把这些页面当作仅补一份 Model 即可运行 |
| D09 | 年度回顾 | `AnnualReviewModel`、`annual_load/annual_share`；导入已有回顾可展示，未来回顾由本地历史统计生成。首次导入没有服务器历史时不能凭现有余额推算完整历史 |
| D10 | 遗留 `koto_*` | 9 个协议有定义，但本次未见直接发送/注册回调。暂列兼容待确认，不擅自当作当前正在使用的探索流程，也不从审计清单移除 |
| D11 | 日志、统计、客服、平台通知 | `client_user_action/client_set_client_envinfo/hall_report_remote_addr` 等改为必要本地诊断或停用；本地系统通知可接入旅行/成熟调度；与界面有关的 SDK 回调必须完成或报告不支持 |
| D12 | 原生生命周期与文件能力 | 后台/恢复/退出保存、系统文件选择与写出、存档导入 UI、照片另存；区分 Android 原生壳与浏览器测试路径，避免只在网页中可用 |

公告里的配置会影响菜单和玩法是否显示，且不完全经过游戏 Socket 协议；原生 SDK 还可能加载远端内容。它们是协议清单之外必须继续处理的依赖。

## 7. 服务器推送与自动推进清单

协议表之外发现的 17 个回调如下，均已有客户端消费者，需决定由本地哪个服务提供：

| 分类 | 回调 |
|---|---|
| 持久玩法状态 | `weather_load`、`easteregg_load`、`furniture_load_flowerpot`、`other_load_touch` |
| 任务/奖励补充 | `cooking_task_update`、`springcard_load_task_item`、`item_gift_open` |
| 事件/奖励/红点 | `notify_new_event`、`notify_new_mail`、`notify_redmsg`、`notify_reward` |
| 公告/广告 | `client_load_publicity`、`adsmgr_ads_notify` |
| 系统通知 | `client_notice`、`notify_marquee`、`notify_kick`、`notify_reload` |

此外，在协议表内的 `item_update/clover_update/item_update_ticket` 等也可承担状态下发，不能误以为只有这 17 个才是推送。

自动推进至少需要这些本地任务族；类型、具体周期和公式应由规则层定义：

| 任务族 | 必须执行的动作 |
|---|---|
| 蛙生活/旅行 | 动作结束、出发、旅途阶段、寄照片、归家和奖励、特殊邀请/聚会结果 |
| 草田与设施 | 成熟、收割再生、堆肥阶段、花盆成熟、口袋积累、制作完成、待摆放/换装、心情变化 |
| 客人与故事 | 到来、超时离开、招待/送礼后的回信与回礼、新故事与手账 |
| 周期与过期 | 每日/每周/每月任务、限购和免费次数重置、商人到离、邮件/称号/活动到期 |
| 天气与表现 | 昼夜/季节/天气切换、相关彩蛋开始和结束 |
| 活动 | 探索到达、料理和手作进度、扭蛋任务、贺卡反馈、蛋糕阶段、许愿冷却等实际需要计时的步骤 |

现有 `TimerEvent` 还包含 `Recharge/AntiAddition/DriftBottle/MuseumMiss` 等在线或特殊类型。导入时必须识别并按兼容策略处理；不能遇到未知类型就阻塞整个结果队列。完整数值枚举见协议附录。

需要区分三个时间点：**业务已结算、结果已展示、玩家已确认**。例如归家奖励可能已经计入余额但动画尚未播放，不能在恢复时再次发放。

## 8. 为将来的在线状态导出/单机导入预留什么

### 8.1 本地存档应包含的数据

下面是建议的逻辑分区，不是已经确认的在线响应字段，也不是已实现的文件格式：

| 分区 | 保存内容 |
|---|---|
| 文件头 | 格式/模式版本、客户端版本、内容/规则版本、导出时间、源时间基准、来源说明、校验值、完整性报告 |
| 身份与设置 | 源账号标识与本地存档 ID、蛙名、创建时间、引导、偏好、称号/头像/展示照片 |
| 钱包与资产 | 全部余额、库存、图鉴、成就、礼包权益、购买/兑换/领奖记录 |
| 容器 | 行囊、桌子、工作台、堆肥箱、礼品盒、来客邀请行囊等的实际槽位 |
| 角色与庭院 | 蛙状态/动作、草田、来客、装饰、家具、所有庭院设施、天气 |
| 旅行与进行中任务 | 行程、制作、成熟等任务上下文和剩余时间、已确定结果、随机状态/结果记录 |
| 照片与文本 | 相册完整实例、各层、未保存/已删除照片、动态照片、手账、故事、贺卡、邮件 |
| 扩展玩法 | C01–C17 的进度、次数、物料、待领奖结果、开放区间和各自版本 |
| 事件与一致性 | 待展示/待确认事件、奖励结算标记、事务/去重记录、时间锚点、下一次刷新 |
| 内容依赖 | 用到的素材/配置版本；包内不存在的必要资源索引或随文件携带的数据 |
| 兼容与缺失 | 未识别字段、旧版/未来版原始状态、导出缺项及恢复策略，避免无声丢失 |

会话 token、支付凭据、设备绑定和 SDK 登录缓存不属于“继续单机游戏”所需的可移植进度。源账号标识与本地存档 ID 分开，防止不同账号导入时覆盖同一份存档。

### 8.2 在线导出器以后必须补的工作

| 编号 | 工作 | 原因 |
|---|---|---|
| E01 | 确定经用户登录后的状态读取路径和目标在线版本 | 本次没有采集真实账号；不能假设现有 APK 的字段与在线现行版本完全一致 |
| E02 | 首次同步采集及完成屏障 | `client_load_all_info` 关联多个模型回包，收到某一个成功回调不一定能代表所有异步/懒加载内容完整 |
| E03 | 补齐按需数据 | 相册 `album_load_all` 可能先返回 ID 列表，须再取完整层数据；邮件分页、回收站、手账、各活动页面数据也需完整枚举 |
| E04 | 一致性快照 | 读取期间可能发生采收、归家、邮件/奖励推送；需要快照修订号或变化重放/稳定窗口策略，避免余额和容器来自不同时点 |
| E05 | 暴露数据与隐藏数据区分 | 客户端未必拿到服务器完整行程、随机种子、未来任务、历史统计；记录“无法导出”，制定有限恢复方案，不能承诺逐字节续接服务器内部状态 |
| E06 | 资源与版本检查 | 导出账号可能拥有包内不存在的照片/家具/活动内容；预先列出缺失依赖并允许可理解的兼容显示 |
| E07 | 文件写出与校验 | 选用可检查且版本化的格式；照片多时可采用容器文件加资源附件；导出后回读校验、缺项报告 |

### 8.3 单机导入器以后必须补的工作

| 编号 | 工作 | 完成标准 |
|---|---|---|
| F01 | 解析与类型/版本校验 | 区分文件损坏、不支持版本、缺少模块、未知资源；缺失不自动等同空列表 |
| F02 | 备份、预览和原子导入 | 显示目标存档与主要进度，导入失败保留旧档；导入中断不留下半新半旧状态 |
| F03 | 规范化与迁移 | 1 基/0 基索引、数组/字典、JSON 字符串、时间单位、照片 ID/实例 ID、未知字段均正确处理 |
| F04 | 时间转换与续接 | 明确从导出瞬间恢复，还是补算导出后经过的时间；沿用已确定结果，缺少隐藏上下文时标明本地重建部分 |
| F05 | 模型重建与资源预载 | 所有解锁、设施、图鉴和活动状态恢复后再开场景；从权威状态重建缓存、红点、索引、计时器 |
| F06 | 完整性和往返验证 | 导出→导入→再导出的核心状态一致；只允许时间推进和规范化造成可解释差异；不同账号互不混写 |

本地核心可先建立这套存档边界，无需等在线导出器完成。新档模板和真实账号导入应走不同入口，共用校验与恢复流程。

## 9. 开发顺序与验收里程碑

M4 的格式和校验设计应从 M0 开始；真实在线采集可后续实施。M1 可以先解决用户看到的设施缺失，但“打开面板”不作为设施玩法全部完成的验收。

跨阶段必验场景：新档、旧空档、真实导入档；合法未解锁状态；进行中的旅行/制作；奖励动画中退出；重复点击和重启；长时间离线；跨日/月；同模板多张照片；未知内容 ID；有未领邮件和未确认事件；存档写入失败及恢复。

## 10. 尚需确认，不能用猜测充当原版规则的内容

1. 新档究竟赠送哪些基础物品、余额和设施；教程完成后是否额外解锁工作台/堆肥箱。客户端的常量或当前默认值不能直接当作原服务器初始存档。
2. 旅行选择、持续时间、道具效果、照片/掉落权重、来访概率、隐藏关系/成就进度。
3. 家具配方、生产排程、心情/罢工、堆肥阶段/产出/草田效果、口袋积累和花盆生长规则。
4. 各活动的服务端任务生成、真实期限/刷新、抽奖概率和限额；哪些规则确实包含在 `config.eab`，哪些只有展示数据。
5. 没有在线社交、分享、广告和支付时，新奖励怎样获得、过去活动是否常驻、未支持模块怎样呈现。
6. 原账号可见快照能否拿到进行中的完整行程和排程；若不能，应使用何种可解释的本地续接策略。
7. `koto_*`、包外 H5/原生 SDK 玩法和当前在线版本新增模块的兼容范围。

这些待确认项不妨碍先实现确定的数据容器、事务保存、协议适配与有效状态恢复，但会影响“原版规则复现”的精度。后续每项完成都应记录依据、具体本地规则、存档字段和验收结果。
