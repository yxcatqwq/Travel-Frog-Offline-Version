# 旅行照片导出与前后景对齐说明

本次导出的成品、清单和复核图：

| 内容 | 位置 |
|---|---|
| 全部照片 | `generated_photos/<Goal|Unique|Normal|Tools>/*.png` |
| 逐张清单（模板、图层、变体、SHA-256） | `generated_photos/manifest.jsonl` |
| 无法导出的模板及原因 | `generated_photos/skipped.jsonl` |
| 复核接触表（每模板一张，按类别分页） | `alignment_review/latest/*.jpg` |
| 场景摆位表（可读、可改） | `tools/photo_layout.py` |

本轮共导出 **959 张照片**，覆盖 328 个模板：Goal 142、Unique 119、Normal 39、Tools 28。
每张模板按其配置的全部人物组合导出（伙伴三选一 + 青蛙独照）；Normal/Tools 会用固定随机种子多轮采样，
内容完全相同的重复样本不会重复写出，因此 959 张全部互不相同（清单里给出每张的 SHA-256）。

## 1. 客户端是怎么合成照片的

`offline_build/web_game/js/main.min.js` 里的 `Tabikaeru.getPictureTexture` 是唯一权威实现：

```js
v.texture = RES.getRes(Tabikaeru.PathToName(resources[f.layer[0]]));
v.x = f.layer[1];      // 绝对左上角坐标
v.y = f.layer[2];
// 画布固定 500x350
```

也就是说一张照片就是若干张 PNG **按绝对坐标贴到 500x350 画布上**。图层表由服务端下发
（`picture_load` / `checkPictureByIds` 的 `layers` 字段），客户端包内只有模板数据
`Picture.json`：`backImage`、`frontImage`、`frogPose/travelerPose`、`frogPos/travelerPos`。

因此人物坐标可以直接照抄配置，而**背景/前景的坐标必须重建**——这正是之前几个版本错位的根因。

## 2. 之前版本的错位原因

1. 景物层用「居中到画布」的猜测坐标。对于从整幅画里裁出来的图层（屋顶、树、土坡、竹笋……）
   这个猜测会让硬切边落在画面中间，出现直角接缝、地面悬空、人物“站在水里/空中”。
2. 少数场景被逐个硬编码修补（`if record["id"] in (100,101) ...`），只覆盖了两三个模板。
3. 8 个场景因为“缺少摆位元数据”被整条跳过，Unique 的多图层场景同样被跳过。
4. `generated_photos/` 目录里混着旧版本生成的文件，命名规则和坐标都与当前脚本不一致。

## 3. 现在的重建规则（`tools/photo_layout.py`）

`auto_position()` 先用「硬切边」判断每一层在原画中的裁切方向——某条边上有 ≥35% 的不透明像素
才算被裁切，而不是羽毛状边缘或投影——然后：

| 情况 | 摆法 |
|---|---|
| 图层本身就是整幅 500x350 | 贴在原点 |
| 左右都被裁切、且比画布宽（全景背板） | 水平居中 |
| 左侧硬切 | 左边缘贴画布左边（切边藏在画外） |
| 右侧硬切 | 右边缘贴画布右边 |
| 上侧硬切（树冠、竹竿、雨幕） | 上边缘贴画布顶 |
| 下侧硬切（地面、沙滩、长凳） | 下边缘贴画布底 |
| 其余（无硬切的漂浮道具、花簇、叶片） | 居中，或写入复核表 |

规则覆盖不到的层写在 `SCENERY_POSITIONS` 里，键是「模板 id + 图层文件名」，值是画布绝对坐标。
这些数字是逐张看图核对后定下的，例如：

* `100 back_n_roof1`：松树 `tree01` 落在 `(79,54)`、树冠 `tree02` 落在 `(0,0)`，树干切边沉到屋顶线以下；
* `102/103/104` 海滩：海面抬到 `y=120`、栏杆 `rail01` 底部对齐画布，人物按配置正好站在沙滩上；
* `107/108` 竹林：竹竿上端切边贴画布顶，下端被土坡盖住，竹笋落在土坡上；
* `3202 back_u_chuisihaitang`：木板 `chuisihaitang_mid_1` 底边贴画布底，睡猫正好趴在木板上。

雨伞类道具是这套规则里唯一的例外：`Tools/1000-1003` 的前景 `wet0_1`、`wet1_1`、`wet2_1`、
`wet3_1` 不是景物，而是青蛙手里那把伞（或荷叶）本身。伞面外层布面和角色贴图里已经画好的
伞里衬是同一把伞的两面，要在伞沿处对齐，所以这几层直接沿用角色贴图的坐标原点
（`frogPos` 换算出的左上角），`1000` 的荷叶则让竹竿顶端插进荷叶背面。旧版本把它们当景物，
按硬切边/居中摆放，于是伞盖被丢到树枝下面的水面上。

人物仍然严格使用配置坐标：`x = 250 - w/2 + pos.x`、`y = 175 - h/2 - pos.y`（居中原点、Y 轴向上）。
这个约定由 `Goal/2000 beijing1` 等实拍样例验证：青蛙与旅伴正好坐在背景画好的石台上。
角色的先后顺序按画面来定：默认先画青蛙再画伙伴（伙伴在上），但有些模板的伙伴贴图是从青蛙
身后绕过去的，必须反过来画，这些模板列在 `generate_photo_composites.py` 的 `FROG_ON_TOP_IDS` 里。

## 4. 仍然无法导出的照片

`generated_photos/skipped.jsonl` 逐条列出，共 23 个模板：

* **8 张景点照片缺底图**：`2033 xianggang3`、`2035 xianggang5`、`2039 haerbin4`、
  `2040–2042 changbaishan1-3`、`2075 hainan3`、`2076 hainan4`。
  对应的 `g_*.png` 不在本包的 `resource/China/images/Picture/Goal/` 里，属于客户端未随包发布的素材。
* **14 张月度插画是空白占位图**：`u_month2_2`…`u_month8_2`、`u_two_month2_2`…`u_two_month8_2`
  在资源里是纯白图（均值 254.5、标准差 0.86），并非有效画面。
* **1 个模板复核后判定为多余**：`2120 bwg_shanxi2` 按要求删除，不再出现在 `generated_photos/` 中
  （理由写在 `skipped.jsonl` 里）。

除此之外的模板都完整导出，包括之前被跳过的竹林、朱鹮、雾凇、风铃木、垂丝海棠、木棉花，
以及 `Unique` 中的多图层场景（风雨兰棚、垂丝海棠睡猫、木棉 1–3）。

## 5. 重新生成

```powershell
cd tools
python generate_photo_composites.py --output ..\generated_photos   # 生成照片与清单
python review_photo_composites.py ..\generated_photos ..\alignment_review\latest   # 复核接触表
```

辅助检查脚本（都只读资源、不写游戏目录）：

* `dump_layout.py`：打印每个多图层模板的图层与最终坐标（含是否走了复核表）。
* `audit_layout_coverage.py`：列出仍在用自动规则的图层，便于继续人工复核。
* `audit_character_bounds.py`：列出超出画布的人物贴图（配置本身导致的裁切）。
* `isolate_layers.py <id>` / `inspect_scene_pieces.py <id>`：逐层叠加、逐层查看，用于定位错位。
* `montage_from_manifest.py --ids <id>`：把某模板的全部变体拼成一张对比图。

生成脚本会自动清理输出目录中不在本次清单内的旧 PNG，因此重复运行不会再把旧坐标的文件留在结果里。

## 6. 复核结论

`alignment_review/latest/` 中的 15 张接触表覆盖全部 329 个模板：Normal/Tools 的前后景已对齐
（屋顶线、地面、沙滩、栏杆、竹竿、雨幕等均落在原位），Goal/Unique 的整幅底图与人物按配置坐标准确叠加，
`Goal/2000 beijing1` 的结果与包内 `Guide/guide_out2.png` 的示例照片一致。
